# MASTER PROJECT SPECIFICATION

# Multi-Branch Bus Transportation Management & Online Ticketing System

## 0. IMPORTANT INSTRUCTION TO THE AI CODING ASSISTANT

You are working on an existing software project.

The existing project is the reference implementation for:

* visual design
* component patterns
* application shell
* authentication style
* role-based navigation
* API communication pattern
* PostgreSQL approach
* reusable UI components
* responsive behavior
* dashboard style
* map integration
* transaction/history concepts

DO NOT throw away the existing architecture without a strong technical reason.

DO NOT rewrite the entire project simply because the business domain is changing.

DO NOT invent a completely different frontend architecture.

DO NOT replace working components unnecessarily.

First understand the existing codebase, then extend/refactor it carefully.

The goal is to transform the existing concept into a:

**Multi-Branch Bus Transportation Management & Online Ticket Booking System**

The finished application must be capable of managing one large transportation company with many cities, towns, branches, bus gates, counters, buses, routes, trips, employees, agents, drivers, conductors and passengers.

The owner/head office must be able to control the entire organization from one central administration portal.

# 4. MULTI-BRANCH REQUIREMENT

The system must be designed as a centralized multi-branch platform.

Each branch/gate can have:

* its own address
* phone number
* manager
* counters
* staff
* operating hours
* assigned buses
* assigned routes
* booking activity
* daily sales
* expenses
* cash records

The head office must be able to view all branches.

A branch manager must only see permitted branches.

Counter staff must only see the counter/branch assigned to them.

Agents must see their own bookings, commission and assigned operations.

Customers must only see their own bookings and customer information.

# 90. BOOKING CONCURRENCY

This is critical.

Two customers must not be able to successfully purchase the same seat.

Seat booking must be protected by server-side transactional logic.

Required behavior:

Customer A chooses seat A1
Customer B chooses seat A1

Only one request succeeds.

The other receives:

"Seat A1 is no longer available."

Never depend on the frontend for this protection.

Use appropriate PostgreSQL transaction/locking/unique-constraint strategies.

# 150. DEFINITION OF DONE

A feature is not complete merely because a page exists.

A feature is complete when:

* frontend exists
* backend endpoint exists
* database model exists
* validation exists
* authorization exists
* organization scope works
* loading state works
* empty state works
* error state works
* mobile layout works
* audit behavior exists where appropriate
* tests exist for critical business rules

---

# 151. FINAL SYSTEM GOAL

The finished system should feel like a professional transportation company's central operating platform.

The owner should be able to sit at head office and understand:

What buses are running?
Which branches are active?
Which trips are departing?
How many seats are sold?
How much money was collected?
Which routes are popular?
Which branch is selling the most?
Which agents are performing?
Which buses require maintenance?
Which trips are delayed?
Which customers are travelling?
Which tickets are cancelled?
Which refunds are pending?

At the same time:

A counter staff member should only need a few clicks to sell a ticket.

An agent should easily book a passenger.

A driver should immediately know today's trip.

A conductor should quickly verify passengers.

A customer should easily search, choose a seat, pay and receive a ticket.

The entire organization must operate from the same centralized source of truth.

Before implementing features, inspect the existing BiteN Go codebase and preserve useful architecture and UI patterns.

Do not copy the old canteen/ferry business model.

Transform the existing platform into the multi-branch commercial bus transportation system described above.

Implement incrementally.

After every major phase:

* run type checking
* run tests
* verify database migrations/schema
* verify authorization
* verify API
* verify responsive UI
